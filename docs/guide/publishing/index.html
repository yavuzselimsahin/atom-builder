Publishing

atom publish uploads the archives. It is the one stage atom release does not run for you, because anything that leaves your machine should be a deliberate act.

What gets uploaded

The archives in dist/ and SHA256SUMS — not the raw binaries in dist/<target>/. Those are intermediates. See Packaging.

GitHub Releases

[publish.github]
repo = "you/your-project"
tag  = "v1.2.0"          # optional; defaults to v<version>

export GITHUB_TOKEN=ghp_...
atom publish

atom looks for a release with that tag, creates one if there is none, and attaches every archive to it. The result is a normal GitHub release page with downloadable assets.

The token needs permission to create releases on that repository. A fine-grained token with Contents: read and write is enough.

Push your commits first. If the tag does not exist yet, GitHub creates it at the head of your default branch — not at your local HEAD. Publishing with unpushed commits gives you a release whose tag points at older code than the binaries were built from.

If an asset with the same name is already attached, atom stops and says so rather than guessing whether you meant to replace it.

Your own server

[publish.ssh]
host = "user@vps"
path = "/var/www/dl/myproject"

The files are mirrored there with rsync, and the directory is created if it does not exist. Nothing is deleted — this is a copy, not a sync, so an older release sitting in the same directory stays downloadable.

Point a web server at that path and you have download links.

Publishing locally

Leave host out and path is treated as a local directory:

[publish.ssh]
path = "/Volumes/releases/myproject"

Useful for a mounted volume or a directory another tool watches.

Both at once

Configure both sections and both run. Configure neither and atom publish tells you so, with the sections to add.

Look before you leap

atom publish --dry-run

ssh: would upload 3 files to user@vps:/var/www/dl/myproject/
  myproject-1.2.0-linux-arm64.tar.gz
  myproject-1.2.0-windows-x86_64.zip
  SHA256SUMS

Nothing is contacted and nothing is uploaded. Without --dry-run, atom lists the same files with their sizes and asks for confirmation. -y skips the question, for scripts.

How your token is handled

The token is passed to curl on standard input, through --config -. It never appears in the process arguments, where any other user on the machine could read it out of ps, and it is never written to disk.

A token containing a quote or a newline is refused rather than escaped, since anything that would need escaping to pass safely is more likely a mistake than a real token.

atom reads GITHUB_TOKEN, falling back to GH_TOKEN.

One thing to know

The GitHub path has been built and tested in every respect except the one that needs a real account: token handling, confirmation, dry-run, response parsing and command construction are all covered by tests, but no request has been sent to the live API from the development machine. The rsync path is tested end to end.

What is not here yet

Code signing. An unsigned Windows executable triggers SmartScreen warnings, and unsigned macOS binaries are refused by Gatekeeper. Both can be signed from Linux — osslsigncode for Authenticode, rcodesign for Apple notarization — and both are planned. Until then, atom ships what your compiler produced.

Package manager manifests. Homebrew taps, Scoop buckets and AUR PKGBUILDs are generated by hand for now.
